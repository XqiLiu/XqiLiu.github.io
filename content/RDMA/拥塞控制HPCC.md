# 基本概念

## 下一代CC算法的期待
在论文中，作者将主要痛点缺陷归类为如下三点：
1. **收敛速度慢**：在传统算法依赖ECN标记，这是较为模糊的反馈，发送端只能指导有拥塞，但不知道拥塞程度。
2. **难以避免排队**：传统算法通常在队列堆积后才开始降低速率，这直接破坏了对延迟敏感的应用的性能。
3. **调参复杂**：DCQCN有15个参数需要调整。

所以作者希望新一代CC有如下4个目标：
1. 延迟应尽可能低；
2. 带宽/利用率应尽可能高；
3. 拥塞和 PFC 暂停应尽可能少；
4. 操作复杂性应尽可能低。
## INT（In-band Network Telemetry）
新一代交换机芯片支持的信息检测功能：
- 在DCQCN算法中，交换机只会在数据包上打一个1bit的ECN标记，表示堵了，从而刷新T和BC计数器
- 现在交换机在数据包的ACK中插入精确的元数据，其中主要包括：
	- 时间戳（ts）
	- 队列长度（qLen）
	- 已发送字节数（txBytes）
	- 链路带宽（B）
	所以HPCC建立在这一事实基础上，使得发送端可以精确算出链路的利用率，而不是像DCQCN一样需要分三步走来猜测，所以导致启动较慢。

# HPCC设计实现

## 框架设计
HPCC类似于DCQCN，依然是一个**发送方驱动**的CC框架。
![](HPCC_f4.png)

发送发发出pkt，经由交换机打上INT消息后，在接受方发送ACK后，发送方收到消息后进行发送速率调整。
## 核心算法
HPCC**基于inflight bytes控制**，是一种**基于窗口**的CC策略。
HPCC并不是控制速率，对飞行字节（inflight bytes）空的好处是**大大提高了拥塞期间对于延迟反馈的容忍度**，因为：
- 基于飞行字节控制，可以确保了inflight字节的数量在限制之内，使得发送方在限制达到时立即停止发送。
- 基于速率控制的方案，可能会由于网络堵塞，致使反馈延迟被推演很久，从而造成不稳定。

**算法的核心判断逻辑**：
- - 如果不发生拥塞，在飞字节数 $I$ 与速率的关系为 $I = rate \times T$ （$T$ 为基础 RTT）。
- 如果 $I < B \times T$（$B$ 为链路带宽），说明管道没填满，没有拥塞。
- 如果 $I \ge B \times T$，说明发生了拥塞或排队。

**快速反应但不过度反应**：
如果没有这一设计，基于每个ACK进行即时反馈调整可能会导致发送端把发送窗口降低得过低，从而损失性能。
例如如下图所讲述得**负面场景**：

![](hpcc_f5.png)
- a中发送端$S_1$ 发出的两个数据包 $P_1$ 和 $P_2$ 都在同一个交换机队列里排队。此时队列长度（qLen）是 4。
- b中是第一次反馈，P1离开队列，它的ACK携带了qLen=4的消息回到发送端，发送端收到消息后会认为网络拥塞，于是根据算法把窗口 $W$ 减半。
- c中是问题的**关键**，此时发送端收到P2的ACK，这是第二次反馈，发送端会以为拥塞还在持续（其实是同一段拥塞的结果），于是**再次**把窗口减半。
$P_1$ 和 $P_2$ 其实反馈的是**同一个**拥塞事件（同一波排队数据）。发送端因为连续收到两个 ACK 就连续降速两次，这就导致了窗口变得过小，这就是“过度反应”。HPCC 后续通过引入Reference Window（$W^c$），结合 Per-RTT 更新机制解决了这个问题。
简单的理解，就是一个RTT才调整一次，但这样有个弊端，每个 RTT 更新一次窗口对于处理故障和 incast 等紧急情况可能太慢。

**算法实现**:
[](hpcc_al1.png)这里的算法就是利用INT数据来精确计算链路输出速率的核心。
这里几个变量可以解释一下：
 公式：
$$txRate = \frac{ack_1.txBytes - ack_0.txBytes}{ack_1.ts - ack_0.ts}$$
这里的变量都来自交换机通过 INT 插入到数据包中的元数据。
$ack_1$ 和 $ack_0$ 是发送端连续收到的两个ACK，需要注意二者携带的是**同一个交换机端口**的信息。
利用发送字节数之差和时间算出交换机端口在两个数据包之间的**实际输出速率**。

公式：
$$u' = \frac{\text{qlen} + txRate \times T}{B \times T}$$
该公式利用上述的速率算出归一化的inflight字节数，之后$u = \max(u')$来找出**最堵**的那一个。之后用**EWMA**平滑处理：
$$U = (1 - \frac{\tau}{T}) \cdot U_{\text{old}} + \frac{\tau}{T} \cdot u$$
接下来开始进行新窗口调整，这里有两种调整方法，乘性（快速）和加性（微调）：
算法会检查两个条件：
1. **$U \ge \eta$**：说明网络负载已经很高了，或者拥塞了（必须刹车或大调）。
2. **`incStage` $\ge$ `maxStage`**：说明我们已经连续微调增加了很多次窗口，网络还没堵，需要快速增加负载。
再额外讲一下乘性分支：
$$W = \frac{W^c}{U/\eta} + W_{AI}$$
- 如果 $U$ 很大（拥塞），分母 $U/\eta > 1$，窗口 $W$ 会急剧缩小（快收敛）。
- 如果 $U$ 很小（空闲），分母 $U/\eta < 1$，窗口 $W$ 会直接跳升（利用空闲带宽）

## 参数控制
HPCC只有三个需要设置的参数：$\eta$、maxStage、$W_{AI}$，运维难度低
1. **$W_{AI}$(Additive Increase Window)**
$W_{AI}$ 是发送窗口在进行加性增长时的步长。这个设计巧妙地把**带宽利用**和**公平性**解耦。
- 利用$U$进行乘性调整，负责快速把带宽占满或消除拥塞。
- 利用$W_{AI}$负责在多条流竞争时，让大家慢慢趋于公平。

2. **$\eta$（Target Utilization）**
发送端期望链路达到的最大负载比例。通常设置为 **95%**.
故意放弃 5% 的带宽，换取**绝对的零队列**，避免在 100% 满载运行，由于数据包到达的随机性，容易发生微小的碰撞从而产生短暂的排队。

3. **maxStage**
一个计数器阈值。它规定了在切换到乘性增加之前，必须连续进行多少次加性增加 。通常设为 **5**
目的是为了**防止震荡**：当网络已经接近满载时，我们不希望窗口忽大忽小。
